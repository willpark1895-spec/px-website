## Phantom Data / Calculation Findings

These are spots where the system fabricates inputs or asserts confidence that isn't grounded in user data. None corrupt the math itself — but each one makes the output look more authoritative than it is.

### Phantom #1 — Ecosystem handler hardcodes `confidence: 'high'`
**File:** `api/index.js`, `handleEcosystem()`

```js
dataQuality: { confidence: 'high', syntheticDataUsed: false, ... }
```

The handler returns `confidence: 'high'` regardless of how the user got their canopy %. A measured NLCD value and a 30-second eyeball estimate produce identical confidence flags. **Fix:** accept an optional `canopySource: 'measured' | 'estimated'` field and downgrade to `'moderate'` when estimated.

### Phantom #2 — Appreciation handler silently fills `currentCanopyPct` and `lotSizeSqFt`
**File:** `api/index.js`, `handleAppreciation()`

```js
currentCanopyPct: body.currentCanopyPct != null ? Number(body.currentCanopyPct) : 25,
lotSizeSqFt: body.lotSizeSqFt != null ? Number(body.lotSizeSqFt) : 15000,
```

If callers omit these, the API substitutes `25%` canopy and `15,000 sqft` lot — then still returns `syntheticDataUsed: false`. The downstream calculation runs on synthetic inputs without flagging. **Fix:** either require these fields (return 400) or set `syntheticDataUsed: true` when defaults are applied.

### Phantom #3 — `engine.analyze()` invents biodiversity & GI presence
**File:** `lib/terravalue-engine.js`, line 1707–1717 (`TerraValueEngine.analyze`)

```js
hasGreenInfrastructure: parcelData.canopyPct > 25,
biodiversityNetGainPct: parcelData.canopyPct > 30 ? 12 : 5,
projectedScore: Math.min(100, canopyBasedScore + 10),
```

The orchestrator guesses GI presence from canopy %, picks a biodiversity number from the same threshold, and assumes a +10 score bump for the projection. These are then fed to `CertificationPathway.assess()` and `LandAppreciation.project()` and reported back without a flag. The handler at `/api/analyze` does not add a `dataQuality` block at all. **Fix:** mark these synthesized inputs with a top-level `dataQuality.assumptionsApplied` array on the analyze response.

### Phantom #4 — Projector slider derives canopy from a separate score (pre-existing, Audit Finding #5)
**File:** `website/terravalue.html`, `_runProjector()`

```js
currentCanopyPct: curr * 0.4,   // slider (0-100) × 0.4 = pretend canopy %
lotSizeSqFt: 15000,             // hardcoded "average" lot
```

`curr` is the "Current Soil Score" slider, but the code treats `curr × 0.4` as a canopy percentage — there's no derivation behind the 0.4 multiplier. Combined with the hardcoded 15K-sqft lot, the projector is a stylized illustration, not a property-specific projection. Already noted in handoff as Finding #5 — but the UI does not disclose this assumption. **Fix:** add a small "illustrative — uses 15K sqft typical lot" caption beside the projector.

### Phantom #5 — Land valuation form silently fills missing fields with demo values
**File:** `website/terravalue.html`, `lvBtn` click handler

```js
lotSizeSqFt: parseInt(...) || 18000,
buildingSqFt: parseInt(...) || 2400,
assessedValue: parseInt(...) || 180000,
yearBuilt: parseInt(...) || 1995,
canopyPct: parseInt(...) || 25,
condition: 3, locationQuality: 3,   // not user-editable
```

If a user clears a field and clicks Run, they get a confident-looking valuation built on demo inputs. `condition` and `locationQuality` aren't even exposed in the form. The engine's own `dataQuality.warnings` only fires for missing comparables/income — it doesn't catch defaulted parcel inputs. **Fix:** disable the Run button until all fields are filled, or add a "uses demo values" badge when any default fires.
