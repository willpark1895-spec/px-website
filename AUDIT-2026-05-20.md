# P&X / TerraValue — Full-System Audit

**Date:** 2026-05-20
**Scope:** code + config + docs + live production; standalone deploy + pxconsulting.io API
**Method:** read everything, run the tests, hit the live endpoints, look for drift between what docs claim and what the system does

---

## TL;DR

The system is healthy in production. The API at `pxconsulting.io/api/*` passes 23/23 E2E checks against live traffic. Terravalue.app loads, renders, and falls back gracefully. The May 9 value corrections (carbon $494, energy $252, 12% premium cap) are live and arithmetically consistent across the engine and config.

But the audit surfaced three categories of weakness that should be addressed:

1. **The offline parity test suite is broken.** Deleting `website/terravalue-engine.js` today removed the reference engine that the tests compare against. `npm test` errors immediately. The "26/26 tests pass" claim repeated in every recent handoff has been stale since the deletion. **Severity: high (CI/safety regression).**
2. **The API silently returns garbage on invalid input.** String inputs produce `null` services; negative canopy produces negative service values; canopy > 100 scales linearly with no cap. Empty-body validation works; content validation doesn't. **Severity: medium-high (data integrity, customer-facing).**
3. **Constants traceability has regressed.** The whole point of the May 4 refactor was to move constants to config. Six magic numbers crept back into the engine, including the 5% ecosystem cap rate that the audit specifically flagged as needing sourcing. **Severity: medium (methodology drift, but not a math bug).**

Plus a handful of smaller findings — wasteful rate-loading on the standalone, a missing `capped` flag the May 9 handoff said had shipped, and the perennial input-bounds and rate-limit security gaps. Detail and prioritized fixes below.

## Findings

Sorted by severity. "Production impact" = does this affect what a real user sees today.

### F1 — Parity tests broken (HIGH severity, no production impact)

**What:** `tests/golden-parity.test.js` line 14 still requires `../website/terravalue-engine` — the file deleted in commit 1 today. Running `node --test tests/golden-parity.test.js` errors immediately with `MODULE_NOT_FOUND`.

**Why this matters:** Every recent handoff claims "26/26 golden parity tests still pass." That claim is unverifiable until the test suite is repaired. There is no offline regression check on the engine anymore. The only safety net is `tests/e2e-validate.js`, which (a) requires a live URL and (b) only does shape checks, not value-exactness checks.

**Fix path (one of three options):**

- **A (lightest):** Delete the parity tests entirely. They've served their purpose — they validated the API migration. Going forward, the live E2E suite is the canonical check.
- **B (recommended):** Convert parity to golden-snapshot. Run the engine once across the existing fixtures (PARCELS, PROJECTIONS, SITE_DATA, FULL_VALUATIONS), serialize the outputs to `tests/golden-snapshots.json`, and assert `lib/terravalue-engine` matches those snapshots on each run. Same fixtures, same coverage, no dependency on a second engine. The first commit also pins the current behavior as truth.
- **C (heaviest):** Resurrect the monolith somewhere as a frozen reference. Doesn't make architectural sense given the engine is now the authoritative version.

I'd recommend B. ~30 minutes of work, restores the offline check, gives you a real regression net before any future engine edits.

### F2 — API accepts garbage input and returns garbage output (MEDIUM-HIGH, live production)

**What:** Three confirmed reproductions against live `pxconsulting.io/api/ecosystem`:

| Input | Expected | Actual |
|---|---|---|
| `"lotSizeSqFt": "abc"` | 400 error or coerced-then-rejected | 200 with all `value: null` |
| `"canopyPct": -50` | 400 error or clamped to 0 | 200 with negative service values (-$247 carbon) |
| `"canopyPct": 500` | 400 error or clamped to 100 | 200 with values 5× the 100% canopy result ($2,470 carbon) |

**Why this matters:** The customer-facing surface treats every 200 as a successful calculation. There's no way for a frontend (or AVM partner integrating the API) to distinguish "we calculated it" from "we returned nulls because your input was junk." For an AVM positioning itself on USPAP rigor and audit-grade methodology, this is the kind of finding an institutional buyer's DD will land on.

**Why it happens:** `Number(body.lotSizeSqFt)` at api/index.js:195 happily produces `NaN` from `"abc"`. NaN then propagates through `Math.round`, `Math.min`, etc. JSON serializes NaN as `null`. The `requireFields` check at line 116 only checks for `null/undefined`, not for "is this actually a positive finite number."

**Fix:** Add a `validateNumericRange(value, { min, max, name })` helper. Apply it to every numeric field at parse time:
- `lotSizeSqFt`: `> 0`, finite (cap at ~10M sqft = 230 acres, anything larger probably indicates a unit error)
- `canopyPct`: `0–100` inclusive, finite
- `assessedValue`: `>= 0`, finite (zero is legit for vacant land)
- `state`: must be a 2-letter string
- All other numeric optionals: finite, sane ranges (`currentScore`, `projectedScore`: 0–100; `timelineYears`: 1–100; etc.)

Return 400 with a clear field-level error message. The pattern is in the existing `requireFields` function; extending it is straightforward.

### F3 — Constants traceability has regressed (MEDIUM, methodology audit risk)

**What:** Six places in `lib/terravalue-engine.js` use inline magic numbers that should come from config. Inventory:

| Line | Magic number | Should be |
|---|---|---|
| 1195 | `assessedValue / 0.40` (GA assessment ratio) | `LAND_VALUATION_CONSTANTS.georgia.assessmentRatio` |
| 1232 | `ecosystemAnnualValue / 0.05` (5% ecosystem cap rate) | New config field `ecosystemCapRate` |
| 1513 | `Math.round(ecoServices.totalAnnual / 0.05)` | Same as above |
| 1624 | `Math.round(ecoValue / 0.05)` | Same as above |
| 1099 | `Math.round(lotSizeSqFt * 5)` ($5/sqft fallback land value) | New config field `landValueFallbackPerSqFt` |
| 1556 | `subject.assessedValue / 0.40` AND `subject.lotSizeSqFt * 15` ($15/sqft synthetic comp baseline) | First: ratio; second: new config field |
| 1701 | `(parcelData.canopyPct / 40) * 100` (canopy → score heuristic) | New config field or documented constant |
| 1711 | `parcelData.assessedValue / 0.40` | Same ratio |

The 5% ecosystem cap rate is the one the audit specifically flagged ("professional judgment, sourcing TBD"). Right now it's *fewer* findable across the codebase than it would be if it were in config — three separate inline literals. If you (or a regulator, or an AVM-vendor buyer doing diligence) want to know "where is the 5% cap rate?", grep returns three results in lib/, and zero in config/. After the fix, grep returns one result in config/ with a `source` field next to it.

**Fix:** Add an `ecosystemCapRate: 0.05` (or whatever value you decide) to `config/land-valuation-constants.json` under a new `ecosystemPremium.capRate` key. Add a `source` field with the citation (or `"P&X professional judgment v1.0"` if you're being honest about it being unsourced for now). Replace the four inline literals. Same for the GA assessment ratio and the $5/sqft and $15/sqft fallbacks. ~30 minutes including config edits.

This is also a Soil Principle moment — the foundation (config) should hold every research-backed constant; the engine should be pure math.

### F4 — `capped: bool` flag was never actually shipped (LOW, doc/code drift)

**What:** The 2026-05-09 handoff says: *"`propertyPremium` output now carries `capped: bool` flag."* I grepped the engine — no `capped` field is emitted anywhere. The cap math is correct (line 153, `Math.min(rawPremiumPct, maxPremiumPct/100)`) but the output never exposes whether the cap fired.

**Why this matters:** Small but real spec drift. Someone reading the handoff and then the code would conclude the flag exists. For an audit-honest product, "the cap fired on this calculation" is exactly the kind of metadata an institutional buyer wants on every output.

**Fix:** Add `capped: cappedPremiumPct < rawPremiumPct` to the propertyPremium output. One line, no behavior change.

### F5 — `terravalue-standalone` does a wasteful API call just to read rate constants (LOW, perf)

**What:** `loadRates()` at index.html:1032 POSTs to `/api/ecosystem` with placeholder values (43560 sqft, 100% canopy, $100K assessed) **purely to extract the rate constants** from the response. The engine runs a full calculation, returns full payload, and the frontend throws everything except `services.*.ratePerCanopyAcre`. Every terravalue.app page load triggers this.

**Why this matters:** It's not breaking anything, but it's the kind of inefficiency that looks bad in an architecture review. Two costs: (a) wasted engine cycles on the API side; (b) bigger response payload over the wire.

**Fix:** Add a `GET /api/rates` route that returns just the ECOSYSTEM_SERVICE_RATES object (with `_version` for cache busting). Switch `loadRates()` to a GET. The API gets faster, the frontend gets simpler, the rate object becomes a first-class part of the API surface (which is what an AVM partner integrating against you would want anyway).

### F6 — `handleHealth()` runs a full ecosystem calculation just to extract version (LOW, perf + smell)

**What:** api/index.js:424-426 calls `EcosystemServices.calculate({...placeholder...}).methodology` purely to get the version string `"1.0.0"`. The version is already a top-level export from `config/index.js` (`METHODOLOGY_VERSION`).

**Fix:** Import `METHODOLOGY_VERSION` from config at the top of api/index.js and use it directly. Five-line change.

### F7 — No rate limiting (MEDIUM, security)

**What:** `TERRAVALUE_API_KEY` is currently unset (per the kickoff). With auth disabled, anyone can hammer any endpoint. Vercel provides edge-level DDoS mitigation but no per-IP or per-key rate limits.

**Why this matters:** A botted abuse pattern, or even a single misconfigured frontend in production, could blow through Vercel's monthly function invocation budget overnight. The engine itself is cheap per call but the surface is wide open.

**Fix path:**
- Short-term: set `TERRAVALUE_API_KEY`. The auth code at api/index.js:54 is already constant-time and ready. Update terravalue.app's `fetch` calls to either (a) include the `X-API-Key` header — but then the key is exposed in browser DevTools — or (b) whitelist the terravalue.app origin in the `isSameOrigin` check (more conservative: only same-origin requests skip auth, so external callers MUST send a key). Option (b) is the right one for the institutional posture.
- Medium-term: add a simple in-memory rate limiter per `req.headers['x-forwarded-for']` IP (Vercel sets this) — e.g., 60 requests/minute. Cheap, defends against accidental misuse.
- Long-term: when API becomes a real product, move to a real rate-limit provider (Upstash, Cloudflare, etc.) with per-key quotas.

### F8 — No request size limit on parseBody (LOW, security)

**What:** `parseBody` at api/index.js:124 reads the entire stream into memory with no size cap. Vercel's edge applies a 4.5MB body limit so this is bounded at the platform level, but the application code doesn't defend against a 4MB legitimate-looking body that still wastes engine time. Realistic attack is low (no obvious amplification vector), but worth a 5-line fix.

**Fix:** Cap at e.g. 100KB and return 413 above that. Comparable to industry standard for JSON APIs.

### F9 — Score-to-canopy conversion math is documented in one place and applied in another (LOW, design clarity)

**What:** The standalone uses `canopyPct = score × 0.4` (so score 100 = 40% canopy) for its in-page display logic. The engine's `LandAppreciation.project()` uses `canopyChangePct = scoreDelta × 0.5` (delta function). These are different mappings — one is an absolute conversion, one is a marginal one. The relationship between them is non-trivial and not documented anywhere except in code.

**Why this matters:** If you ever ship a third surface (e.g., the institutional API partner doc, the white paper for the validation study), the canopy-score relationship needs a single canonical statement. Right now you have to read both files to reconstruct what the model actually does.

**Fix:** Either document the mapping in `terravalue-standalone/methodology-audit.md` and reference it from both call sites, or push the mapping itself into the engine as a `LandAppreciation.scoreToCanopy()` static method that both surfaces call. Latter is cleaner.

### F10 — Process env read on every request (TRIVIAL, perf)

**What:** `process.env.TERRAVALUE_API_KEY` at api/index.js:59 is read inside `authenticate()`, which runs on every request. In serverless cold-start scenarios this is fine, but it's wasted work.

**Fix:** Module-level constant. One line.

## Efficiency opportunities (separate from bug-fixes)

Distinct from the findings above — these are things that work correctly but could work better.

### E1 — Engine module loading

Each Vercel function cold-start re-parses 1,771 lines of `lib/terravalue-engine.js`. Vercel does keep warm instances, but cold-starts are ~100ms higher than warm (you can see this in the load test: 175ms first request, 100ms by request 5). If you ever care about p99 latency, splitting the engine into smaller modules and lazy-loading the LandValuation pipeline (the heavy part) would help.

Not worth doing yet. Worth keeping in mind for when the validation study generates partner traffic.

### E2 — Synthetic comparable generation

`_generateSyntheticComps` (engine line 1553) is deterministic except for `Math.random()` at line 1572 (`buildingSqFt: subject.buildingSqFt * (0.9 + Math.random() * 0.2)`). That random seed means the same input produces different output across requests. For a methodology that emphasizes traceability, **non-determinism in the demo data path is a smell.**

Fix: replace `Math.random()` with a deterministic function of the inputs (e.g., a simple hash-based perturbation). Same statistical effect for demo purposes, fully reproducible.

### E3 — Engine calculates `ECO_SERVICE_TOTAL_PER_ACRE` once at load but per-service deltas every call

`config/index.js:26` computes the $2,004 sum once at module load. Good. But `LandAppreciation.project()` recomputes the per-service breakdown (lines 283-287 of the engine) on every call. The math is `canopyAcreDelta × rate` which is fast, but the *structure* of the breakdown could be pre-built as a vectorized form.

Microoptimization. Not worth doing unless profiling shows it hot.

### E4 — Redundant `LandValuation.fullValuation` work in `handleAnalyze`

`handleAnalyze` (api line 360) calls `engine.analyze()` (line 378), then separately calls `LandValuation.fullValuation()` (line 394). The first call doesn't include land valuation, but the parcel data is duplicated and the request paths overlap. Could be refactored to a single orchestrator that takes "include land valuation: bool" as a parameter and runs everything in one pass with shared intermediate state (especially the `marketValue` calculation that happens in three different modules).

Worth doing as part of a v1.1 cleanup, not urgently.

### E5 — Standalone bundles a 2,345-line engine that's used as fallback only

The standalone HTML loads the full engine via `<script src="terravalue-engine.js">` so the fallback path can call it on API failure. That's ~155 KB on every terravalue.app page load. For a marketing surface, that's a lot.

Alternative: serve the engine from the API as `GET /api/engine.js` so it's only loaded when needed. Or strip the engine down to just the methods the standalone actually calls (`ECOSYSTEM_SERVICE_RATES`, `LandAppreciation.project`, `LandValuation.fullValuation`) and ship a smaller `terravalue-engine.min.js`.

Worth doing if Lighthouse scores ever become a marketing concern.

## Vulnerabilities (things that need strengthening, separate from bugs)

### V1 — Open-access API (cross-references F7)

Stated above. Listing again because it's the single most exploitable thing in the stack.

### V2 — Float-pumping (cross-references F2)

The "negative canopy → negative service values" finding from F2 isn't just a UX bug. If a third-party AVM integrating against the API has any chance of receiving signed numbers from upstream data (sometimes happens with adjusted/normalized canopy metrics), those negatives propagate through and produce negative dollar values that look like calculated outputs. A USPAP-defensible AVM cannot return -$247 for "carbon sequestration" without an explicit error.

Same fix as F2.

### V3 — Synthetic comp non-determinism (cross-references E2)

Methodology drift on the demo path. Two requests, same input, different output. For an audit-traceable product, every output should be a deterministic function of every input.

Same fix as E2.

### V4 — Error responses include `err.message`

api/index.js:493 returns `error: err.message` in the 500 response body. JS error messages can sometimes include file paths, function names, or stack-trace fragments from upstream libraries. Low information leakage in practice, but it's not zero.

Fix: log `err.stack` to Vercel logs (already happening at line 490), but return a generic message to the client: `"Internal server error. Reference: <request-id>"` where `<request-id>` is `x-vercel-id` or a UUID you generate.

### V5 — No content-type validation

The API accepts any content-type with a parseable JSON body. Should require `Content-Type: application/json` or return 415. Tiny, but it's a CSRF defense-in-depth measure if you ever enable cookie-based auth.

### V6 — Documentation surface exposes assumptions a competitor would love

`terravalue-standalone/methodology-audit.md` is served live at `terravalue.app/methodology-audit.md`. It is correctly framed as a transparency feature — that's the AVM positioning. But it also explicitly documents:

- The exact rate values per service
- The 12% premium cap
- The score-to-canopy conversion
- The synthetic-comparable generation pattern

A competitor can clone the methodology in a weekend. **This is a strategic decision, not a bug.** The May 5 positioning brief says transparency is the moat. Worth re-asking: is the moat "we publish our methodology" or "we have the validation study and the design partners that prove the methodology"? If it's the former, methodology-audit is the right surface. If it's the latter, you might want to gate the audit doc behind a contact form so you at least capture leads from people reading it.

Not urgent. Worth thinking about before the AVM-vendor pitches in Q3.

## System-level observations

These aren't findings or fixes — these are things about the architecture itself worth thinking through.

### S1 — Two engines, one source of truth

`lib/terravalue-engine.js` is the Node version (config-driven). `terravalue-standalone/terravalue-engine.js` is the browser version (constants inlined). Today they're behaviorally equivalent — the May 4 refactor explicitly extracted the constants but the browser bundle still ships with them inlined.

That equivalence is preserved by convention, not by build. If the Node engine gets a tweak that doesn't propagate to the browser bundle, the fallback path on terravalue.app will silently disagree with the primary API path. The only thing that would catch it is the (broken) parity test suite.

**Architectural fix:** generate the browser bundle from the Node engine at build time, with the config baked in. Then there's one source. The build step is small: load the Node engine + config, serialize the config as `const ECOSYSTEM_SERVICE_RATES = {...}` inlined into the browser file, run a `terser` to minify, write to `terravalue-standalone/terravalue-engine.js`. Could be a `package.json` script or a Vercel build hook.

This is the right v1.1 fix. It also opens the door to versioning the bundle (`/terravalue-engine-1.0.0.min.js`) for proper cache busting.

### S2 — The validation study is the system's reason for existing, but it's not in the code or docs

The strategic spine (per the v0.2 prioritization) is the validation study + the broker design partner. Neither has a code surface, a data model, or a pipeline. That's correct for now — they're operational, not technical. But once paired-sales data starts arriving, you'll need:

- A schema for paired-sales records (canopy/non-canopy comp pairs, sale prices, adjustments)
- A storage layer (Vercel KV, Postgres, or just JSON in the repo)
- A regression endpoint that fits the model against the paired-sales data and emits an `aboutTo:` lift number
- A way to surface that lift number on terravalue.app's "Validation" section

**Worth thinking now about how the validation study integrates with the live engine.** Two options:

- (a) Separate offline study; the engine doesn't change; the marketing surface displays the published lift number as a static stat.
- (b) Online study; paired-sales data drives engine coefficient updates; the engine's `marginalValuePer1Pct` becomes a learned parameter rather than a published constant.

Option (a) is what the positioning brief implies. Option (b) is what would make TerraValue actually an AVM in the technical sense, not just an AVM in the marketing sense. **Worth deciding before the data starts arriving, not after.**

### S3 — The Soil Score is shipped as a stub

`EcosystemServices.calculateSoilScore` (engine line 187) returns `null` with the comment "Coming soon." The marketing page mentions "Soil Score" prominently. The methodology doc references it. The score is in the feature prioritization matrix as #15 P1/P2.

This is fine — a "coming soon" stub is honest. But the gap between "Soil Score is a thing we say we do" (marketing surface) and "Soil Score returns null" (technical surface) is exactly the kind of thing that erodes the audit-honest posture if a buyer notices. Either the stub needs to be made operational, or the marketing copy needs to soften from "Soil Score" to "Soil Score (in development)" anywhere it currently reads as live.

I'd recommend the latter for now, and revisit when the SSURGO/NLCD/PAD-US pipeline lands (P1/P2 in the matrix).

### S4 — The system has zero observability

There's no logging beyond `console.error` (which goes to Vercel logs but isn't searchable beyond Vercel's UI). No metrics. No traces. No alerts.

For something serving production traffic and pitching itself as institutional-grade, this is below table stakes. The good news: it's cheap to fix. Vercel has built-in analytics that capture function invocations, error rates, and latency. Turning them on is one toggle. For deeper observability, Logtail or Axiom integrate in minutes.

**Recommend:** turn on Vercel Analytics today. Worth adding a simple counter in each handler (`{route}.{outcome}`) that you can grep in logs to answer "how many ecosystem calls today" without a third-party tool.

### S5 — Two README files, two trees, one repo

`P&X/README.md` is the canonical source-of-truth at root. `P&X/terravalue-standalone/README.md` is the canonical doc for the standalone surface. They reference each other. That's correct — the alternative is one giant README which fails the Soil Principle on legibility grounds. But: the **mental model** of "one repo, two Vercel projects, two Root Directories" is non-obvious. A new contributor (or future-you on a tired Tuesday) will find it confusing.

**Suggestion:** add an ASCII tree to the root README's "Where things live" section that visualizes the dual-deploy structure. The current text-table version is correct but the spatial layout would land faster.
